# Indy7 팔레타이징 시스템 트러블슈팅 및 작업 프로세스 리뷰 보고서

- **작성 일시**: 2026-09-03
- **대상 설비**: 뉴로메카 Indy7 협동로봇 (`192.168.3.7`)
- **작업 내용**: 2단 팔레타이징/디팔레타이징 (2x2 그리드, 총 8개 피스), 양솔레노이드 공압 그리퍼 제어, PLC I/O 인터록 연동
- **대상 스크립트**: `pallete.py`

---

## 1. 프로젝트 개요

다이렉트 티칭을 통해 수집한 좌표와 PLC 신호를 기반으로, 공급대(`SUPPLY_POINT`)에서 물품을 픽업하여 팔레트에 1층(4개)과 2층(4개)으로 총 8개를 적재하고, 전량 만재 시 회수대(`RETRIEVE_POINT`)로 디팔레타이징하는 자동화 시퀀스를 구축했습니다.

이 과정에서 발생한 기구학적, 전기적, 통신 프로토콜상의 문제점들을 디버깅하고 최적화한 기술적 내역을 기록합니다.

## 2. 발생했던 핵심 이슈 및 기술적 원인 분석 (Deep Dive)

### 📌 이슈 1. 관절 각도(`q`)와 직교 Task 좌표(`p`) 혼용
- **현상**: 다이렉트 티칭 스크립트에서 출력된 관절 각도(`Joint q`, 단위: deg) 리스트를 `pallete.py`의 `PALLET_BASE_POINTS`와 `RETRIEVE_POINT`에 그대로 입력하여 로봇이 역기구학(IK) 불능 에러를 내거나 바닥 밑으로 이동하려 함.
- **원인**: `pallete.py`는 `movel`(직교 직선 이동)과 `pose[2] += 40.0`(Z축 적재 높이 간격) 연산을 수행하므로 **Task 직교 좌표(`[X, Y, Z, U, V, W]`, 단위: mm, deg)**가 필요함. 각도를 대입하면 3번 관절 회전각에 40mm를 더하게 되어 자세가 완전히 붕괴됨.
- **해결**: 티칭된 관절각을 로봇 제어기 순기구학(`robot.forward_kin(q)`) 연산을 통해 밀리미터 단위 직교 좌표계로 정밀 복원하여 입력함. (복원 결과 Z=304mm 수평면의 2x2 패턴 확인)

### 📌 이슈 2. 양솔레노이드 공압 그리퍼 핀 극성 반대
- **현상**: 타겟 위치에 도달해도 그리퍼가 닫히지 않고 열린 상태 그대로 상승하여 물품을 파지하지 못함.
- **원인**: 설비 하드웨어 배선은 `DO 0 = Open`, `DO 1 = Close`였으나, 초기 코드에서 반대로 제어 명령이 인가됨.
- **해결**:
  - `SOL_OPEN_DO = 0`, `SOL_CLOSE_DO = 1`로 배선 사양에 맞게 정렬.
  - 공압 실린더가 완전히 닫히고 에어 압력이 찰 때까지 물리적 대기 시간(`time.sleep(0.6)`)을 보장하여 낙하 방지.

### 📌 이슈 3. [상세 설명] PLC 신호 루프 오인식 버그 (`state: 2`)

이 문제는 **Indy 제어기 통신 프로토콜(Protobuf)의 Enum 정의**와 **파이썬의 Boolean 형 변환 특성**이 겹쳐서 발생한 치명적인 버그였습니다.

#### 1) 기존 코드의 로직
```python
def read_do(address: int) -> bool:
    res = robot.get_do()
    for sig in res.get("signals", []):
        if sig.get("address") == address:
            return bool(sig.get("state"))  # 💥 문제 발생 지점
    return False
```

#### 2) 발생 원인 분석
1. **IndyDCP3 내부 프로토콜 (`DigitalState` Enum)**:
   뉴로메카 제어기 gRPC 프로토콜(`device_msgs_pb2`) 내부에는 디지털 신호 상태가 3가지 정수로 정의되어 있습니다:
   - `OFF_STATE = 0` (전원 꺼짐 / Low)
   - `ON_STATE = 1` (전원 켜짐 / High)
   - **`UNUSED_STATE = 2` (미설정 / 미사용 핀 기본 상태)**

2. **파이썬의 `bool()` 형 변환 특성**:
   - 파이썬에서는 `bool(0)`만 `False`이며, **0이 아닌 모든 숫자(`1`, `2`, `-1` 등)는 무조건 `True`로 평가**됩니다.
   - 즉, `bool(2) == True`가 성립합니다.

3. **실제 로봇 제어기의 핀 상태**:
   - 로봇 제어기의 DO 신호를 실시간 스캔한 결과, 배선되지 않고 비어 있는 DO 2번~31번 핀들은 모두 **`state: 2 (UNUSED_STATE)`** 상태였습니다.
   - `read_do(8)` ➡️ `sig['state']`가 `2` ➡️ `bool(2)` ➡️ **`True` 반환!**
   - `read_do(9)` ➡️ `sig['state']`가 `2` ➡️ `bool(2)` ➡️ **`True` 반환!**
   - `read_do(3)` ➡️ `sig['state']`가 `2` ➡️ `bool(2)` ➡️ **`True` 반환!**

4. **결과**:
   - PLC에서 버튼을 누르지도 않았고 신호를 주지도 않았는데, 파이썬 루프는 **"8번(적재)도 켜졌고, 9번(회수)도 켜졌고, 3번(허가)도 켜졌다"**고 오인식하여 1초 만에 8개 적재와 회수 루프를 무한 반복하며 폭주했습니다.

#### 3) 추가적인 배선 방향성 (PLC DO ➡️ 로봇 DI)
- PLC의 출력 신호(PLC DO)는 전선을 타고 로봇 제어기 기준 **디지털 입력 핀(`Robot DI`)**으로 들어옵니다.
- 따라서 `robot.get_do()`가 아닌 `robot.get_di()`를 확인해야 실제 PLC 신호를 읽을 수 있습니다.

#### 4) 최종 해결 코드
미사용 상태인 `2(UNUSED)`와 `0(OFF)`은 엄격하게 배제하고, **오직 전원이 인가된 `1(ON_STATE)`일 때만 참(`True`)으로 판별**하도록 수정하여 유령 신호 버그를 완벽하게 근절했습니다:
```python
def read_signal(address: int) -> bool:
    """state == 1 (ON_STATE)인 실제 신호만 True 반환"""
    # 1. PLC 출력 -> 로봇 DI 우선 확인
    res_di = robot.get_di()
    for sig in res_di.get("signals", []):
        if sig.get("address") == address:
            return sig.get("state") == 1  # 2(UNUSED)와 0은 False

    # 2. 로봇 DO 확인
    res_do = robot.get_do()
    for sig in res_do.get("signals", []):
        if sig.get("address") == address:
            return sig.get("state") == 1
    return False
```

### 📌 이슈 4. 모션 도달 비동기 큐잉 및 그리퍼 타이밍 불일치
- **현상**: 공급 위치로 내려가서 그리퍼를 닫아야 하는데, 로봇이 하강하는 도중에 허공에서 그리퍼를 닫고 다시 열어버림.
- **원인**: 기존의 `robot.wait_progress(progress=100)`는 명령이 제어기 큐에 들어가기 전 이전 모션의 완료 플래그(100)를 읽어 **단 0.003초 만에 반환(Return)**해 버림. 파이썬 코드가 로봇보다 수 초 앞서 실행되어 적재 단계의 오픈 명령까지 미리 전송해 버림.
- **해결**: 제어기의 실제 물리 주행 상태(`robot.get_motion_data()['is_in_motion']`)를 모니터링하여, 로봇 속도가 0이 되고 목표 위치에 **완전히 정지할 때까지 동기화 대기**하도록 개편.

---

### 📌 이슈 5. 동작 허가(3번 신호) 인터록: "사이클 완료 정지(Cycle-Complete Stop)" 설계
- **현상**: 적재 사이클 진행 도중 3번 신호가 꺼졌을 때 물건을 집어 들고 상공에서 멈춰 서버림 (낙하 위험 및 안전 저해).
- **원인**: 세부 모션(`linear_move`) 사이사이에 3번 검사가 들어가 있어 모션 도중 급정지됨.
- **해결**:
  - 산업용 자동화 표준인 **"사이클 완료 정지"** 로직 적용.
  - 진행 중이던 피스는 팔레트에 끝까지 안전하게 안착을 완료함.
  - **그 다음 번 피스를 공급받으러 가기 직전(사이클 시작부)에만 3번 신호를 검사**하여, OFF일 경우 빈 그리퍼로 안전 높이에서 일시정지 대기하도록 수정.
  - 3번 신호가 기본 OFF인 **회수(Retrieve) 시퀀스에서는 3번 인터록 검사를 제외**하여 원활한 연속 회수 보장.

### 📌 이슈 6. 공급대 경사 진입각(Tool -Z) 충돌 및 공구축 후퇴
- **현상**: `SUPPLY_POINT`에서 접근/후퇴할 때마다 그리퍼가 공급대 측벽을 심하게 긁으며 충돌 발생.
- **원인**: 
  - 공급 위치의 툴 자세는 **`U = -21.77°`로 약 21.8도 경사진 상태**로 물품을 파지함.
  - 기존 코드는 단순히 `target[2] += 100.0`으로 **베이스 Z축(순수 수직 위 방향)**으로만 들어 올림.
  - 경사진 상태에서 수직으로만 뽑아 올리다 보니 $\Delta X = 100 \times \sin(21.77^\circ) \approx 37\text{ mm}$의 수평 편차가 발생하여 측벽을 들이받음.
- **해결**:
  - 엔드툴의 기울기를 그대로 유지한 채 **공구 중심축(Tool -Z축) 방향으로 대각선 후퇴**하도록 `get_offset_pose()` 함수를 개편.
  - 제어기 내장 기구학 연산(`robot.calculate_current_pose_rel(..., base_type=TaskBaseType.TCP)`)을 적용하여, 진입각의 연장선상(`[X: 276.21, Y: 525.20, Z: 349.80]`)으로 미끄러지듯 진입/후퇴하여 충돌 제로 달성.

### 📌 이슈 7. 연속 적재 모드 (방식 A)
- **개선**: PLC 8번 기동 신호가 1회 펄스(푸시버튼)로 들어오더라도 `is_stacking = True` 상태 플래그를 유지하여, 8개 만재(`stacked_count == 8`) 시점까지 멈추지 않고 1번부터 8번까지 연속으로 수행하도록 구성.

## 3. 작업 프로세스 회고 (왜 오래 걸렸는가?)

### 1) 일반 웹 대화창(LLM) 코드의 태생적 한계
- 웹 대화창의 AI는 **실제 로봇 환경, 설치된 패키지 내부, 하드웨어 배선과 완전히 격리**되어 있습니다.
- "문법적으로 그럴듯한 코드"를 생성하지만:
  - `DigitalState.UNUSED_STATE = 2`의 Enum 사정을 모름
  - `wait_progress(100)`의 비동기 즉시 리턴 특성을 모름
  - 공급대가 21.8도 기울어져 있다는 물리적 사실을 모름
- 결과적으로 잠재적 결함이 잔뜩 묻어있는 코드가 실기 환경에 투입되어 연쇄 버그를 유발했습니다.

### 2) Top-Down (전체 실행) 중심의 사후 디버깅
- 단일 동작(그리퍼 단독 테스트, 1개 포인트 진입/후퇴 테스트)을 먼저 검증하지 않고 8개 전체 시퀀스를 바로 가동하여, 복합적인 원인이 얽힌 채 문제를 하나씩 마주쳤습니다.

## 4. 향후 작업 3배 단속을 위한 Best Practice 제안

외부에서 작성된 코드나 예제 코드를 가져와 Antigravity와 협업할 때는, **로봇을 작동시키기 전에 반드시 아래 프롬프트를 1회 먼저 요청하는 프로세스를 권장합니다.**

### 💬 [추천] 사전 검증(Pre-flight Check) 프롬프트 템플릿

```text
"외부에서 가져온 코드인데 실제 로봇에 실행하기 전에 [사전 검증(Pre-flight Check)] 먼저 해줘.

1. 설치된 neuromeka SDK / Proto 스펙 대조 (비동기 블로킹, Enum 판별식 등 결함 검토)
2. 티칭 좌표의 유효성 검토 (관절각/직교좌표 혼용 여부 및 경사 진입각 간섭 가능성)
3. 로봇 IP(192.168.3.7)의 실시간 DI/DO 핀 상태를 스캔하여 신호 로직 대조
4. 단일 동작 단위 테스트 코드 먼저 준비

확인해서 우리 환경에 맞게 안전한 코드로 먼저 리팩토링해줘."
```

이 절차를 거치면 오늘 겪었던 7가지 버그를 **로봇을 단 1회도 움직이지 않고 코드 레벨에서 5분 만에 사전 차단**할 수 있으며, 첫 번째 실행에서 원샷 성공을 달성할 수 있습니다.
